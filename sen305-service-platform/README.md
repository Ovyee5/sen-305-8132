# Enterprise Service Request and Maintenance Platform (VUA-SEN305)

Lab 3 **In-Lab Exercise (Part N)** completed on top of the Lab 2 + Lab 3 project.
Stack: Python 3.12+, Django 5.2, MySQL 8 (utf8mb4).

> All data created by this project is **synthetic laboratory data** (titles start with `SYNTH`,
> owner `synthetic_requester`). No real personal data is used.

## 1. Run it on your own machine

```bash
# from the repository root
python -m venv .venv
source .venv/bin/activate            # Windows PowerShell:  .venv\Scripts\Activate.ps1
cd backend
pip install -r requirements.txt
cp .env.example .env                 # Windows: copy .env.example .env   -> then put YOUR password in .env
```

Create the database and user exactly as in Lab 3 Part C, **plus one extra grant** (Django's test runner
creates a separate `test_sen305_servicedesk` database, and the Lab 3 grants do not allow that):

```sql
GRANT ALL ON `test_sen305_servicedesk`.* TO 'sen305_app'@'localhost';
FLUSH PRIVILEGES;
```

Then:

```bash
python manage.py check
python manage.py migrate                      # applies 0001 and 0002
python manage.py showmigrations requests_app  # both [X]
python manage.py test requests_app -v 2       # 27 tests: 5 original + 22 new
python manage.py lab3_exercise                # prints the evidence for Tasks 1-3
python manage.py lab3_exercise --reset        # removes the synthetic rows again
```

## 3. Design decisions worth explaining in your report

* **Rule placement (Task 2, step 9).** The RESOLVED/CLOSED rule is in `ServiceRequest.clean()`. Django calls
  `clean()` from `full_clean()`, from every ModelForm and from Django Admin, so one definition protects all
  entry points. Admin has no copy of the rule; a test proves Admin rejects invalid input because of the model.
* **"Overdue" is not just `due_at < now`.** A request resolved after its deadline is finished, so overdue
  means *past due **and** still open / assigned / in progress*. That definition lives once in
  `ServiceRequestQuerySet.overdue()` and is reused by Admin, the property and the tests.
* **Why `(status, due_at)` in that order.** Equality/`IN` on `status` first, then a range on `due_at`:
  this is the shape of the overdue query, so MySQL can range-scan the index.
* **Limit to remember.** `clean()` runs when something calls `full_clean()` (forms, Admin, services).
  A bare `ServiceRequest.objects.create(...)` or `.save()` skips it, like every Django `clean()`.
  Services should call `full_clean()` before `save()`.
* **Heads-up for Lab 4.** Lab 4's `service_request_resolve` sets `status` and `resolved_at` but not
  `resolution_summary`. With this rule it will now raise `ValidationError`. When you reach Lab 4, set
  `locked.resolution_summary` (for example from the technician's `work_notes`) before `full_clean()`.
* `TIME_ZONE` is left at UTC deliberately: a different zone makes MySQL need time-zone tables for the
  Admin date hierarchy.
